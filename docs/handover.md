# 引き継ぎ書 — 学習アプリの作り方

**この文書は `kikenbutsu_kou_exam_app`（系譜の 7 つめ）から持ってきたものです。**
このリポジトリ（**高圧ガス製造保安責任者 乙種化学・乙種機械**）は **8 つめ**にあたります。

試験の中身は引き継げませんが、**作り方は毎回同じ**です。
`CLAUDE.md` は「このアプリをどう作るか」、この文書は「**学習アプリ全般をどう立ち上げるか**」を書いています。

**このアプリで新しく分かったことは、ここへ書き足してください。**9 つめを作る人が読みます。

> **注意：この文書の例は、1 つめから 7 つめまでのものが混ざっています。**
> 「四肢択一」「数式は出ない」「合格基準は非公表」といった前提は、
> **この試験には当てはまりません**（**択一式・1 区分 50 問・科目ごと 60 % 程度**）。
> 違いは `CLAUDE.md` の「**危険物版と決定的に違う 6 点**」にまとめてあります。
> **★ 6 つめ・7 つめ（危険物）の例も、そのままでは使えません。**
> 実施機関も根拠法も別で、**受験資格が無く、科目免除があり、合格基準が「程度」**です。
> そして**1 つのアプリに乙種化学と乙種機械の 2 つの試験が入っています。**

## 1. 立ち上げ — 何を持ってきて、何を捨てるか

**このリポジトリを丸ごとコピーしてから、中身を抜く**のが速いです。ゼロから作らないこと。

### 持ってくるもの（そのまま使える）

- `src/` のうち **`components/` `lib/` `pages/` `store.ts` `types.ts`** … 画面・ルータ・Markdown・図はすべて自前で、依存が React だけなので移植に引っかかりません
- **`scripts/check.ts`** … いちばん価値がある。**まず全部持ってきて、この試験に効かない検査だけ外す**（足りない分は作業しながら足す）
- `scripts/render-check.tsx` … 検査のなかで実際に React 描画する部分
- `scripts/drive.mjs` … 実ブラウザでの操作確認（後述）
- `scripts/emit_textbook.py`、`scripts/make_icons.py`、`scripts/launch.cmd`、`scripts/launch.ps1`
- `scripts/prompts/` … **中身は書き換えるが、骨組みは 16 本そろっている**
- `.github/workflows/deploy.yml`、PWA 一式（`manifest.webmanifest`、`sw.js`）

### 捨てるもの

- `src/data/textbook/*.ts`、`src/data/questions/*.ts` … 中身は全部
- `docs/syllabus-*.md`、`docs/section-plan.md` … 作り直し
- `src/data/drills.ts` の中身 … **計算問題が出る試験なら復活させる。**出ないなら骨格だけ残す

### 立ち上げで必ず変えるところ（忘れると後で痛い）

| 場所 | 何を |
| --- | --- |
| **`src/lib/storage.ts` の `KEY`** | **★ ここがいちばん危ない。**localStorage のキーを分けないと、同じ `localhost` で 2 つのアプリを開いたとき**学習記録が混ざります。**型も画面も同じなので、**何も壊れずに記録だけがおかしくなる** |
| `public/sw.js` の `CACHE` | 同じ理由。キャッシュ名も分ける |
| `src/pages/Settings.tsx` の書き出しファイル名 | 同じ理由。どちらのアプリの記録か分からなくなる |
| `package.json` / `package-lock.json` の `name` | 新しいアプリ名 |
| `public/manifest.webmanifest` / `index.html` の名前 | ホーム画面に出る名前 |
| `scripts/make_icons.py` の色 | **姉妹アプリと色を変える。**ホーム画面に複数並ぶので、同系色だと見分けられない |
| `src/styles.css` の `--accent` | **アイコンだけ変えても足りない。**開いた中身が同じ色だと、どちらを開いたのか分からない |
| `.github/workflows/deploy.yml` | **対象ブランチを実際の既定ブランチに合わせる。**ITパスポート版は `main` を待つ設定なのに既定が `master` で、**一度も動いていませんでした** |
| `vite.config.ts` の `base` | リポジトリ名（GitHub Pages のサブパス） |
| `index.html` の `theme-color` | 明暗 2 本。`.topbar` の色と合わせる |
| `scripts/drive.mjs` の `EXPECT_TITLE` | 前のアプリの題名が残ります |

### ★ 「捨てるもの」は本文だけではない — 機能が試験の事実を抱えている

**姉妹アプリの機能を、そのまま持ってくると事実誤りになることがあります。**

甲種版を起こしたときの実例です。乙種第 4 類版には、模試に**「科目免除」**という形式を
入れてありました。乙種は、すでに免状を 1 つ持っていると他の類で法令と物化が免除されるからです。

**甲種にはありません。**消防試験研究センターのよくある質問 Q16
「甲種危険物取扱者試験の際に、試験科目の免除はありますか。」→ **「ありません。」**

**コードとしては何も壊れていません。**型も検査も通り、ボタンも動きます。
**アプリが事実と違うことを言うだけです。**

**対策は、画面に出る試験の事実を全部 `grep` で洗うこと。**
問題数、試験時間、科目名、受験資格、手数料、合格率、免除の有無。

**★ それでも洗い残します。**甲種版は立ち上げのときにこの grep をやったのに、
**8 つめを起こすためにコピーした段階で、乙 4 の記述が 5 か所見つかりました。**
しかも**そのまま公開していました。**

| 残っていた場所 | 見落とした理由 |
| --- | --- |
| `index.html` の **`<meta name="description">`** | **画面に出ません。**検索結果とリンク共有のときだけ出る |
| `scripts/launch.ps1`（3 か所） | **アプリではなくランチャ。**`src/` を見ていると目に入らない |
| `scripts/make_shortcut.ps1`（2 か所） | 同じ。**ショートカットの名前と説明文** |

**`src/` と `public/` だけを見ていると、この 3 ファイルは漏れます。**
**試験名そのもので、リポジトリ全体を grep してください。**
`grep -rn -I '<前のアプリの試験名>' --exclude-dir=node_modules .` の 1 行で済みます。
**前のアプリの試験名は、自分では思いつかない場所に残ります。**
甲種版では、この洗い出しで次が見つかりました。

- ホーム画面の表に「受験資格 … **なし。誰でも受けられる**」（甲種にはある）
- 同じ表に「受験手数料 … **乙種 5,300 円**」
- 模試の案内に「法令 15 問 / 物化 10 問 / **性消 10 問**」（甲種は 20 問）
- `scripts/drive.mjs` の `EXPECT_TITLE` が `'危険物乙4'` のまま

**どれも型検査も `npm run check` も素通りします。**

## 2. 作業の順番 — この順でないと手戻りする

1. **試験要項を公式で確認する** … 形式・問題数・時間・合格基準・実施回数。**`CLAUDE.md` の冒頭に日付つきで書く**
2. **シラバスを書き起こす** … `docs/syllabus-*.md`。中項目・学習目標・学習項目・詳細キーワードを**全部**。これが後工程すべての土台
3. **章立てと節割りを確定する** … `docs/section-plan.md`。**キーワード数で按分して章の重みを決める**
4. **入門編を手で書く** … ★重要。後述
5. **章ごとのプロンプトを書く** … `scripts/prompts/`
6. **教本を書かせる** … Codex、1 章 1 担当
7. **教本をレビューする** … **書いた人とは別の目で**
8. **確認問題を書く** … **教本を書いた人とは別の側が書く**
9. **問題をレビューする** … また別の目で
10. **体験ウィジェットを作る**
11. **実際にブラウザで動かす**
12. **公開する**

### 4 を飛ばさないこと（入門編を手で書く理由）

`src/data/textbook/intro.ts` は 3 つを兼ねています。

- **文体の見本** … 章のプロンプトに「これを読んで文体を合わせろ」と渡す
- **用語辞典と略語表のリンク先** … 全章から `[語](textbook/i-4)` で張る
- **試験の受け方の説明** … 本文の唯一の「範囲外」パート

**これを Codex に書かせると、見本が無い状態で見本を作ることになります。**先に手で書いてください。

**そのかわり、入門編は自分で書いた分だけレビューで叩かれます。**このアプリでは入門編だけで 29 件の指摘が出ました（受験端末をパソコンに限定していた、など）。**手で書いたところこそ、別の目に通してください。**

## 3. Codex に書かせる

**リポジトリの直下で走らせます。**`--cd` は付けません
（公開するリポジトリにローカルパスを残さないため）。

```bash
codex exec --sandbox workspace-write --color never \
  -o out-02.txt - < scripts/prompts/02-xxx.md
```

| オプション | なぜ |
| --- | --- |
| `-o out.txt` | **最終メッセージだけ**を落とす。途中の思考ログで依頼側のコンテキストを食わない |
| `-` （標準入力） | 長い日本語をシェルの引用符で壊さない |
| `--sandbox workspace-write` | 執筆用 |
| `--sandbox read-only` | **レビュー用。指摘だけさせて、直すのは依頼側。**書き換えまで任せると何が変わったか追えません |

### 並行させるときの鉄則

- **1 ファイル 1 担当。**`src/data/textbook/<章 ID>.ts` を 1 章 1 ファイルにしてあるのはこのためです
- **同時 4 本まで。**5 本並べると利用上限に当たります
- **`npm run check` を実行させない。**並行実行でキャッシュが衝突します。検査は依頼側がまとめて 1 回
- **走っている最中に `npm run check` を叩かない。**ファイルが一瞬消えるので `Could not resolve` で落ちます

### 上限に当たったときの復旧

**上限に当たると、ファイルは書き換わっているのに `-o` の報告だけが残りません。**
何が終わって何が終わっていないか分からなくなるので、`git diff --stat` と `grep -c` で検算してください。

このアプリでも 1 巡目のレビューが **5 本とも全滅**しました。ジョブを分けるときは、
**先に 4 本流して、1 本終わってから 5 本目を流す**のが安全です。

### ★ 上限は「静かに」来ます — `2>/dev/null` を付けないこと（2026 年 9 月 20 日）

**9 本目（高圧ガス甲種）で、いちばん分かりにくい形で当たりました。**

背景に流すとき、こう書いていました。

```bash
codex exec --sandbox workspace-write -o out-12.txt - < scripts/prompts/12-ho-device.md > /dev/null 2>&1
echo "12 終了: $?"
```

**3 本とも「終了: 1」。`out-12.txt` `out-14.txt` `out-15.txt` は 1 つも作られず、
`git status` にも変化がありません。**
これだけでは、上限なのか、プロンプトが壊れているのか、サンドボックスに弾かれたのかが
分かりません。**前のジョブ 4 本は、同じ書き方で普通に通っていました。**

**分かったのは、1 本を前景で、`2>&1` にして流し直したときです。**

```
ERROR: You've hit your usage limit. ... or try again at 10:40 PM.
```

**教訓は 2 つです。**

- **`2>/dev/null` を付けないこと。**理由の全部がそこに出ます。
  `> /dev/null 2>&1` ではなく、**`> out.log 2>&1` にして残す**
- **`-o` のファイルが「作られていない」のは、上限の徴候です。**
  途中で落ちたときは中身が途中まで書かれます（下の read-only の項）。
  **1 バイトも無いのは、始まる前に断られたということ**です

**枠は時間帯ごとの総量です。**このときは **4 章を書かせたところで尽き、
次に使えるのは約 1 時間半後**でした。**1 セッションで 4 章と見積もってください。**

**待っている間は、手で書ける仕事に回すこと。**
このときは、直前の章が薄かったので、その厚みを手で足しました。

### ★★ 上限は 2 段ある。週の枠は 5 日待ち（2026 年 9 月 22 日、9 つめ）

**「1 時間半待てば戻る」と思っていると、足をすくわれます。**

| 枠 | 尽きるまでの目安 | 待ち |
| --- | --- | --- |
| **1 日の枠** | **4 章ほど** | **約 1 時間半** |
| **★ 週の枠** | **8 章ほど** | **★ 5 日** |

9 つめでは、**9 月 21 日に 8 章、9 月 22 日に 2 章**を書かせたところで週の枠が尽き、
**次に使えるのは 9 月 27 日**になりました。**エラーの文面に日付が出ます。**

```
ERROR: You've hit your usage limit. ... or try again at Sep 27th, 2026 2:29 AM.
```

**「at 10:40 PM」なら今日、「at Sep 27th」なら週の枠**です。**必ず読んでください。**

### ★★ 上限は「章の途中で」来る。ファイルが壊れたまま残る

**報告が残らないだけではありません。**9 つめの `gm-strength`（7 節）は、
**3 節書いたところで切れ、配列が閉じないまま**でした。

```ts
export const gmStrength: TextbookSection[] = [
  { id: 'gm-21', ... },
  { id: 'gm-22', ... },
  { id: 'gm-23', ... },   ← ここで終わっている。`];` が無い
```

**`npm run check` は `Could not resolve` で落ち、`npm run build` も通りません。**
**壊れているのが「書かせた章」だと分かるまで、少し時間がかかりました。**

**だから、返ってきたら必ず次の 3 つを数えてください。**

1. **ファイルの大きさ。**他章が 32〜39 KB のところ、これは 14 KB でした
2. **節の数。**`grep -c "^    id: '"` で数えます
3. **配列が閉じているか。**末尾が `];` で終わっているか

**そのうえで、足りない節は手で書きます。**

### `--sandbox read-only` では `-o` が使えません

**レビューは read-only で走らせるのが鉄則ですが、そのとき `-o out.txt` を付けると失敗します。**
出力ファイルの書き込みも、サンドボックスが止めるためです。

```bash
# だめ（終了コード 1。ファイルは作られるが中身は途中で切れる）
codex exec --sandbox read-only -o review-01.txt - < prompt.md

# よい
codex exec --sandbox read-only - < prompt.md > review-01.txt 2>&1
```

**厄介なのは、報告の中身がそこそこ書かれた状態で落ちることです。**
サイズだけ見ると成功に見えるので、**終了コードと、報告の末尾を必ず見てください。**
乙 4 では 4 本まとめて落として、サイズが 11 KB あったので気づくのが遅れました。

### レビューの割り方

**章単位ではなく分量単位で割ります。**章の大きさがばらばらなので、章で割ると偏ります。

このアプリでの実績：

- **教本 41 節 → 5 ジョブ**（3〜11 節ずつ）
- **確認問題 180 問 → 4 ジョブ**（36〜57 問ずつ）

`kikenbutsu_otsu4_exam_app` での実績：

- **教本 43 節 → 6 ジョブ**（5〜9 節ずつ）
- **確認問題 105 問 → 3 ジョブ**（30〜45 問ずつ）

1 ジョブが大きすぎると、後半が雑になります。**40〜50 問／8〜10 節が目安**です。

### ★ 確認問題は「科目の境目」で割ると、ついでに線引きが見える

**分量で割るのが原則ですが、科目が分かれている試験では科目の境目を優先してください。**

`kikenbutsu_otsu4_exam_app` は法令 45 問 / 物化 30 問 / 性消 30 問で割りました。
そうすると、1 つのジョブが**その科目の全問題**を見ることになるので、
**「この問題は隣の科目の問いになっていないか」**を同じジョブの中で判定できます。

実際にそれで 1 問見つかりました。物化に置いた消火剤の問題が
「**この火災にこの消火剤が使えるか**」を問うていて、これは性消側の問いでした。
しかも同じ適応表を法令・性消でも問うていて、**4 問が同じ表の焼き直し**でした。
**分量で割っていたら、どのジョブからも見えません。**

### レビュー側の「範囲外の指摘」を見分ける

**こちらがプロンプトで例示した語が、そのまま誘導になります。**

このアプリでの実例：プロンプトに「英略語の正式名称を問う一問一答があるか確認せよ」と書いたところ、
**Codex が全節に対して「この節には略語の正式名称問題がない」と機械的に報告**してきました（8 件）。
略語を扱わない節にまで求めるのは過剰なので、採用しませんでした。

**採否はこちらで判断してください。**目安：

- **採る** … 一次資料へのリンクがある、節や章をまたいだ食い違いを指摘している、条文・数値・日付の誤り
- **疑う** … 「〜すべきです」だけで根拠が無い、プロンプトの確認項目をそのまま全件に当てはめている、
  学術的には正しいが読者（非技術職）には不要な精密化

#### ★ ルールの書きぶりが強すぎると、同じ誤読を全ジョブが量産する

`kikenbutsu_otsu4_exam_app` の数値台帳に「**この台帳に無い数字は書かない**」と書いていたところ、
**独立した 3 本のレビューが、そろって同じ指摘を大量に返してきました。**
「1 kg ＝ 1,000 g が台帳にない」「例題の『20 ℃の水 500 g』が台帳にない」。

**3 本が同じ誤読をしたなら、読み手ではなくルールの側が悪い。**
ルールが本当に守らせたかったのは「**出典によって値が違うものを決め打ちしない**」で、
単位の定義や例題の任意値は最初から対象外でした。**そう書いていなかっただけです。**

このときの直し方は、指摘を 1 件ずつ却下することではなく、**ルールに適用範囲を書くこと**です。
却下すると次のレビューでまた出ます。

**レビューが同じ指摘を 3 本以上そろって出してきたら、まず自分の書いたルールを疑ってください。**

## 5. 繰り返し出る誤りの型

**同じ型が毎回出ます。**書くときも直すときも、この一覧を手元に置いてください。

### 教本

- **一度確かめた事実が、あとから古くなっていた** … 姉妹アプリで、確認して書いた施行日が**施行の 6 日前に延期**されていた。**「確認済み」と書いた事実にも期限があります**
- **★ シラバスと一次資料が食い違う** … **このアプリで新しく出た型。**シラバスは「AI 社会原則」を 6 項目として挙げるが、
  一次資料（2019 年・内閣府「人間中心の AI 社会原則」）は **7 原則**で名前も違う。
  教本はシラバスの略記を**一次資料の内容として断定**していた。
  **試験で答えるのはシラバスの側。だが一次資料の内容として書いてはいけません。**両方を並べて、違いを明示すること
- **条文の要件の書き落とし** … 著作権法 30 条の 4 から「**又は他人に享受させる**」が抜けていた。系譜で複数回
- **「まとめて言い切る」ことで生まれる誤り** … 4 つの権利を一律に説明したが、1 つだけ例外があった
- **節をまたいだ食い違い** … 同じ用語を章によって違う説明にしていた
- **本文と図の食い違い** … 図の軸が本文と違う
- **`compare` 図の誤用** … `::` は補足であって左右の区切りではない。**要素数が偶数だと検査を素通りする。系譜で 4 回**
- **★ `compare` 図の左右が入れ替わる** … **危険物甲種（7 本目）で 2 件。**
  `compare` は「**0 起点で偶数番が左**」なので、**説明の 1 行を途中に差し込むと、そこから先の左右が全部ずれます。**
  「水が使える／使えない」の図で、**「硫化りんは不可」が「水が使える」列に入っていました。**
  **要素数は偶数のままなので、既存の検査を素通りします。**書いたら描いて見ること
- **★ `matrix` 図に 5 個以上のセルを書く** … **同じく 7 本目で 1 件。**
  `Diagram.tsx` の `Matrix` は **`items.slice(0, 4)` の固定 2 × 2** で、**5 個目以降を黙って捨てます。**
  3 × 2 の表のつもりで書いたところ、**節の主題だった 2 つの操作が画面から消えていました。**
  記法としては正しく、描画検査も通ります。**`check.ts` に要素数の検査を足しました**
- **★ 図の題の「N 通り」が検査に当たらない** … 検査は「**N つ**」しか数えていませんでした。
  「固体の燃え方は **3 通り**」と題した図に 4 対が入っていて素通り。
  **`NUM` の正規表現に「通り・種類・段階・区分」を足しました**
- **`stack` 図の向きが逆** … `stack` は**先頭が最も幅広い**
- **「よくある勘違い」が勘違いでない** … 事実の再掲になっている。`digest.ts` が直前チェックシートに拾うので影響が広い
- **説明なしの初出** … 定義より前に用語が出ている
- **本文がソースの行番号を指す** … 「最大の問題は 3 行目です」。読者の画面に 3 行目はない
- **★ 条文に無い因果を書いてしまう** … **危険物甲種で 1 件。**
  「**届出を怠ると使用停止命令の対象になる**」と書いていたが、**消防法第 12 条の 2 の 9 事由のどこにも入っていない**
  （罰則の対象にはなる）。**しかも同じ章の別の節に、正しい 9 事由の表が載っていた。**
  **表と地の文が矛盾したまま通っていた**のがこの型の怖いところで、**書いた本人は表を見て安心してしまう**
- **★ 条番号の「の」の位置を取り違える** … **同じく 1 件。**
  立会いの根拠を「消防法**第 13 条の 3**」と書いたが、正しくは「**第 13 条第 3 項**」。
  **第 13 条の 3 は危険物取扱者試験の条文**で、まったく別のもの。
  **「第 N 条の M」と「第 N 条第 M 項」は、音が似ていて字も近い。**引くときに必ず確かめること
- **★ 強調が行をまたいで、`**` が画面に出る** … **危険物甲種（2 巡目）で 1 件。**
  `**強調**` を **`inline()` が 1 行ずつ処理する**ので、開きと閉じが別の行にあると閉じられません。
  **本文を折り返して書き直したときに出ます。**描画は成立するので描画検査を通り、型でも防げません。
  **1 行の中の `**` の数が奇数なら弾く**検査を足しました。1 行で済む検査です
- **★ 法令が切っている区分名と、品名の名前を取り違える** … **危険物甲種で 2 件。**
  「**無機過酸化物**は水が厳禁」と書いていましたが、政令別表第五が切っているのは
  「**アルカリ金属の過酸化物又はこれを含有するもの**」です。**品名の名前ではありません。**
  **同じ章の別の節では正しく限定できていた**のに、消火の説明では広い言い方に戻っていました
- **★「全区分」が何の全区分かで結論が変わる** … **同じく 2 件。**
  政令別表第五の対象物の欄は **12 列**（建築物・電気設備＋危険物 10 区分）です。
  「乾燥砂等だけが**全区分**に適応する」は、**危険物の 10 区分**に限れば正しく、
  **12 区分だと誤り**になります（建築物にも電気設備にも○が付かない）。
  **直前で「12 区分ある」と説明していると、そのまま誤読されます。**
  **数えられる語は、何を数えたのか毎回書くこと**
- **★「〜が多い」と書いた性質を、別の場所で言い切る** … **危険物甲種で 3 件。**
  「第 5 類は分子内に酸素を持つ**ものが多い**」と正しく書いた節の**冒頭と一問一答が、
  「持っています」と言い切っていた**、という形です。
  **例外を書いた節ほど起きます。**例外を書いたら、**同じ節の冒頭・まとめ・一問一答を必ず読み返すこと**

### フェンスを生のバックティックで書いて、ファイルごと壊れる

**本文は TypeScript のテンプレートリテラルの中にあるので、
` ```diagram ` や ` ```quiz ` のフェンスは `\`` を 3 つ重ねて書かなければなりません。**
生で書くと、そこで文字列が終わったことになり、続きがコードとして読まれます。

**これは「本文の誤り」ではなく「ファイルが構文として壊れる」という壊れ方をします。**
だから **`npm run check` そのものが動きません。**束ねる段で落ちるためです。
そして esbuild が出すのは、こういうメッセージだけです。

```
X [ERROR] Expected "}" but found "diagram"
    src/data/textbook/law-what.ts:26:3:
      26 │ ```diagram:flow
```

原因が読み取れないうえ、**検査が動かないので検査に頼れません。**

**対策は、束ねる前に走る検査を別に置くことです。**乙 4 では
`scripts/check-source.mjs` を作り、本文を**ただの文字列として**読んで
行頭の生バックティックを弾くようにして、`npm run check` の先頭に置きました。
壊れていても動く検査なので、これだけは分けておく価値があります。

**9 章のうち 1 章だけがこれをやりました。**同じプロンプトを渡しても、
守る章と守らない章が出ます。**プロンプトに書くだけでは防げません。**

### 確認問題

- **誤答の説明もれ** … 4 つのうち 1 つだけ解説で触れていない。**最も多い型**
- **★ 誤答が実は正しい（＝正解が 2 つ）** … このアプリで 2 問。片方は **Adobe Firefly が動画生成に対応したせい**で、
  書いた時点では正しかった問題が壊れていた。**情報の鮮度が、そのまま正解の数を変えます**
- **分類の軸が混ざっている** … 誤答が正解と別の軸の言葉で、両方成り立つ
- **かっこ書きの言い換えが別語だった**
- **語源の思い込み**
- **章をまたいだ重複** … 1 節ずつ見ている限り気づけない
- **★ 直した結果、別の型を作り込む** … 「正解 2 つが同じことの言い換えになっている」を直そうとして、
  **「事例 1 つ＋その目的」**という組み方にしたら、今度は**分類の軸が混ざりました。**
  設問が「水増しに当たるものはどれか」なのに、正解の片方が「水増しを行う目的」では、
  述語を厳密に取れば正解は 1 つです。**正解 2 つは、同じ軸の上で互いに独立していること。**
  **直したら、直した版をもう一度別の目に見せてください。**この型は 3 巡目で初めて出ました
- **★ あとから足した形式が、既存の問題の焼き直しになる** … 複数選択を 8 問足したら、
  **6 問が既存の単一選択問題の正解を 2 文に割っただけ**でした。定義を問う問題は最初の一巡で
  出そろっているので、あとから足す問題は**具体的な場面へ当てはめる形**にしてください。
  形式としてもそちらが向いています（定義は 1 つに絞れますが、当てはめは複数が並び立つ）。
  **この型は機械では拾えません。**言い回しが違うので 2-gram の重複検査を素通りします。
  レビューのプロンプトに「他のファイルも読んで、同じことを問う問題がないか確かめる」と
  書いておくのが唯一効いた手です
- **★ 公開問題に寄せすぎる** … **危険物甲種（7 本目）で 20 問。いちばん重い型でした。**
  「自前で書き起こした」つもりでも、**主題・設問形式（誤り／正しい）・5 肢の内容・正解の位置まで一致**していました。
  原因ははっきりしています。**教本に「公開問題ではこの 5 肢が出て、これが誤りでした」と表で書いてあり、
  問題を書くときにその表を見た**からです。**教本が中継地点になって複製が起きます。**
  - **対策 1**：教本に**公開問題の肢を列挙しない。**「〜という趣旨の肢が誤りでした」と地の文で要約する
  - **対策 2**：問題を書くときは、**公開問題の分析表（`docs/public-questions.md`）を見ながら
    「同じ主題で、違う切り口」を作る。**5 肢をそのまま持ってこない
  - **対策 3**：**正解の位置を必ず散らす。**位置まで一致していると、複製であることが数字で出ます

### 移植するときは、必ず一度走らせて誤検出を数えること

### ★「言い切り」の検査は、正誤の向きを両方見ること

**危険物甲種（7 本目）で、同じ型の裏返しに当たりました。**

それまでの検査は「**誤答に言い切りがあり、正解には無い**」だけを見ていました。
ところが「**誤っているものはどれか**」の問いでは、**正解肢こそが誤った記述**です。
だから**言い切りが正解肢にだけ付いていると、「言い切っているものを選ぶ」で当たります。**
向きが逆なので、既存の検査では 1 件も拾えませんでした。**レビューで 4 問指摘されました。**

```ts
const picksWrong = /誤って|誤りな|適切でない|妥当でない|該当しない|正しくない|含まれない/.test(q.question);
if (picksWrong && wrongAbsolute === 0 && q.choices.some((c, i) => right.has(i) && tell(c))) warn(...);
```

**「正しいものはどれか」では警告しないこと。**そちらで正解側に言い切りが付くのは、
むしろ「言い切りは誤答」という当て推量を外しにいく側で、**推奨される形**です。

### ★「すべて」「いずれも」を検査語から外していると、いちばん多い型を逃す

言い切りの検査語から**「すべて」を外していた**アプリが複数あります。
「すべての入力に対して」のような、ただの記述まで拾ってしまうからです。

**選択肢の中では、全称そのものが言い切りです。**
危険物甲種では、**誤答 4 つが「すべてが」「いずれも」で、正解だけが限定的な記述**という問題があり、
**内容を知らなくても限定的なほうを選べば当たる**状態でした。
`絶対|必ず|常に` 系だけを見る検査は、これを 1 件も拾いません。

**主語や対象を量化している形だけを見れば、誤検出は避けられます。**

```ts
const universal = /すべてが|全てが|すべて[のはを、]|全て[のはを、]|いずれも|いずれの|どれも|例外なく/;
```

**ついでに「絶対」は「絶対温度」を拾います。**物化の章がある試験では必ず出るので、
`絶対(?!温度)` にしてください。**これを入れるまで、正常な気体の問題に注意が出続けました。**

### 閾値を全体集計にしない

**「言い切りが誤答だけに N 個」のような全体集計は、1 問ごとの偏りを拾えません。**
このアプリでも、全体では正解側にも言い切りがあったため素通りしていました。
**1 問ごとに見る検査に書き換えたら 10 問以上出ました。**

同じ理由で、**「正解だけが長い」の閾値は 1.5 倍では緩すぎます。**1.3 倍まで下げてください。
レビューで指摘されたものは 1.35 倍前後に集中していました。

### 全体集計の検査は、1 問ごとの検査に置き換える

**これは 3 代ぶん同じ見落としをしていました。**
`itpassport` / `g` / `genai` の 3 本は、次の形で書かれていました。

```ts
if (longest / n > 0.3) warn(`正解がはっきり長い問題が ${longest} / ${n} 問`);
if (absoluteInWrong >= 10 && absoluteInCorrect === 0) warn(...);
```

**どちらも「全体でひどくなければ黙る」検査です。**1 問ごとに見る形へ書き換えたところ、
`g_exam_app` で 44 件＋3 件、`itpassport_exam_app` で 38 件が出てきました。
**どの問題かが分からない警告は、あっても直せません。** id を出すこと。

### 日本語まわりで漏れやすいところ

**図の題の「N つ」検査が算用数字しか見ていませんでした。**

## 9. 公開

- **コミットの署名は GitHub の noreply アドレスを使う。**実メールアドレスは履歴に永久に残ります
- 個人情報・ローカルパス・API キーを含めない
- **`deploy.yml` の対象ブランチを実際の既定ブランチに合わせる**（前述）
- GitHub で空のリポジトリを作る → `git remote add origin` → `git push -u origin main` →
  Settings → Pages → Source を **GitHub Actions** に
- **★ `git remote add` は GitHub 側に何も作りません。**宛先をローカルに書くだけです。
  リポジトリを作る前に push すると `Repository not found` になります。
  **エディタの UI からだと「消されたか、名前が変わったか、権限が無いか」と出る**ので、
  「作っていない」だとは読み取れません。**`git ls-remote origin` で切り分けてください**
- **★ Pages の Source は、push の前に手で「GitHub Actions」にすること。**
  Settings → Pages → **Build and deployment** → Source です。**ここが既定のままだと、
  何を足しても公開されません。**
  **`actions/configure-pages` の `enablement: true` では代わりになりません**
  （2026 年 9 月 19 日に 8 本目で実測）。Pages サイトの作成には **admin 権限**が要り、
  ワークフローの `GITHUB_TOKEN` は `pages: write` までなので、
  `Create Pages site failed. Error: Resource not accessible by integration` で落ちます。

  | | `enablement` なし（7 本目） | `enablement: true`（8 本目） |
  | --- | --- | --- |
  | 落ちる場所 | **deploy** ステップ | **configure-pages** ステップ（build の中） |
  | build の見え方 | **緑**なのに公開されない | 赤。deploy は skipped |
  | 直し方 | **どちらも Source を手で設定する。同じ** |

  **落ちる場所が前に移るだけで、手作業が消えるわけではありません。**
  設定したあとは**再実行が要ります**（Actions タブの Run workflow、または Re-run jobs）。
  push しただけでは走りません
- **★ 公開されたか確かめるときに、GitHub API をポーリングしないこと。**
  未認証だと **1 時間あたり 60 回**で、間隔なしのループはすぐ使い切ります。
  **公開 URL を直接叩けば十分**です（`curl -o /dev/null -w '%{http_code}'`）。
  Pages が未設定なら 404 で「Site not found」が返り、有効なら 200 でアプリが返ります
- **Service Worker は HTTPS でしか動きません。**同じ Wi-Fi の `http://192.168.x.x:5173` では
  閲覧できてもオフライン保存は効きません。**ホーム画面に入れて使うには公開が必要です**
- `public/icons/` は**透過なしの正方形**。iOS は透明な画素を黒で塗ります

  `Question.answer` が「添字ひとつ」または「添字の配列」を取るようにし、正解の読み取り・

  移植するときの要点は 3 つ。
  **(1) 選択の状態は、単一選択でも配列で持つ**（未選択は空配列）。`number | null` と `number[]` を
  画面ごとに使い分けると、未選択の表し方が 2 通りになって必ず取りこぼします。
  **(2) 採点は完全一致だけを正解とする。**部分点の規則は、どの試験も公表していません。
  決めたらそれはこちらの創作です（合否を判定しないのと同じ理由）。
  **(3) いくつ選ぶかは画面に出さず、問題文に書かせる。**本番が教えてくれる保証がないためで、
  `check.ts` に「複数選択なのに問題文に個数がない」をエラーとして足してあります。
  なお**この型の変更は、押してみないと確かめられません。**`scripts/drive.mjs` で
  「2 つ押したら 2 つ選ばれる」「もう一度押すと外れる」「単一選択は置き換わる」を実際に数えています
- **合否判定を出さない方針** … 合格基準が非公表の試験では、**アプリが勝手に「合格圏」と断定しない。**
  正答率・時間内に解き切れたか・分野別正答率の 3 つだけを出します。**この方針を崩す変更を入れないこと**
- **模試の構成比** … 公表されていないので、シラバスのキーワード数から按分した推定値です。
  **本番の内訳ではないと、コメントにも画面にも書くこと**

## 12. 直したら、必ず 5 本すべてを見る

**画面と記法の実装は 5 本でほぼ同一です。**だから**不具合も 5 本にあります。**
1 本で直して終わりにすると、次のアプリにそのまま持っていくことになります。

2026 年 9 月 12 日に横断で見直したときの実績です。

| 見つかったもの | どこにあったか |
| --- | --- |
| `markdown.tsx` が `\|` 行で無限ループ | **5 本すべて**（ファイルが 1 文字も違わなかった） |
| 解答が学習記録に二重登録される | **5 本すべて**（genai だけ先に直してあった） |
| 確認問題 200 問の正解が**全部「ア」** | `e_exam_app`。検査が無かったので誰も数えていなかった |
| 正解だけが突出して長い | **計 301 件**（下の表）。閾値が代ごとに違っていた |

**いちばん重いのは `e_exam_app` の「全部ア」です。**選択肢は並び順どおりに描かれるので、
**「ア」を押すだけで 200 問すべて正解できました。**演習として成立していません。
`check.ts` がこのアプリだけ 2 代前のままで、正解位置を数える検査が入っていませんでした。

```bash
# 横断で見るときは、各アプリでこれだけ走らせれば足りる
npm run check && npx tsc --noEmit && npm run build
```

**やり方：**まず新しいほうの検査を古いアプリへ移植し、走らせて誤検出を数える（§6）。
そのうえで、出てきた実害を直す。**検査を入れずに中身だけ直すと、次の代でまた戻ります。**

### 移植の前に、同じ検査がすでに無いか確かめること

**「無い」と判断して入れたら、3 本とも同じ検査をすでに持っていました。**
`grep` に掛けた語（「ほぼ同じ**問題**」）が、あちらの文言（「ほぼ同じ**内容**」）と
違っただけでした。**警告の文面ではなく、判定のコード（`sim >=`、`1.3` など）で探してください。**

### 「正解だけが長い」は 5 本で 301 件あった

同じ閾値（**正解 24 字以上・最長の誤答の 1.3 倍以上・差 6 字以上**）で数え直した結果です。

| アプリ | 件数 | 自作の問題数に対する割合 |
| --- | --- | --- |
| `fe_exam_app` | 151 | 23 % |
| `e_exam_app` | 72 | 36 % |
| `g_exam_app` | 44 | 10 % |
| `itpassport_exam_app` | 34 | 10 % |
| `genai_passport_exam_app` | 0 | — |

**直し方は 2 通りあり、どちらを使うかは正解の側を見て決めます。**

- **正解が説明を抱え込んで長い**とき … その説明は `explanation` の仕事なので、選択肢から外す
- **誤答が言い足りない**とき … 正解と同じ密度まで書き足す

**誤答を書き足すときは、誤りである理由を変えないこと。**「〜する」を「〜するようにする」に
引き伸ばすだけで足りる場合がほとんどです。逆に、意味を足すと**誤答が実は正しくなる**という
系譜で何度も出ている型に当たります。

### 数値だけ違う問題は「重複」ではない

節をまたいだ重複の検査が `fe_exam_app` で 14 組を出しましたが、**12 組は誤検出**でした。
稼働率・損益分岐点・伝送時間・待ち行列など、**同じ公式を理論の節と演習の節で
数値だけ変えて出している**ものです。これは意図した繰返しなので直せません。

検査のほうを直し、**問題文と選択肢に出てくる数が違う組は重複とみなさない**ようにしました。
残った 2 組（ド・モルガンの法則の向き違い、請負と準委任の違い）が本物でした。
